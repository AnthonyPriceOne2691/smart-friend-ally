# Инцидент: накат не привозит часть комплекта, которую приезжающий скрипт подключает через `source`

- **Дата:** 2026-10-18 · **Нашедший:** agent:claude-code (сессия smart-frend-ally, поставка `sync-cqg-2.70`) · **Хозяин:** smart-friend-ally
- **Канон:** инструменты флота Prepare `76c42c3` — `field/fleet/plan_update.py` (`assemble`, `needed_by_arrivals`),
  `field/fleet/apply_update.py`; часть `scripts/lint/mutation_shard.sh` (`cqg@2.64`)

## Симптом

Накат `cqg@2.63 → 2.70` на Ally: план — «едет сам 16, порт вручную 0, стоп 0, **новый файл 0**, нужен приезжающим 0,
не развёрнуто 8», среди «не развёрнуто» — `scripts/lint/mutation_shard.sh`. `apply_update.py` скопировал 16 файлов, и
сразу после него доктор — `DEAD`: «состав контура — развёрнуто 53 из 54, НЕ ОБЪЯВЛЕНО 1: mutation_shard.sh — либо
доложи из payload'а (§5.0), либо объяви в scripts/lint/not-applicable.json с причиной».

## Что видел нашедший

`check_mutation_gate.sh` («едет сам», `+22/−5`) с `cqg@2.64` подключает новую часть: `. "$SCRIPT_DIR/mutation_shard.sh"`
(строка 97). План её не привёз по двум причинам сразу:

- **«новый файл» не срабатывает:** старый payload строится манифестом НОВОГО извлекателя по старым текстам канонов
  (`preflight.historical_payload`), поэтому `mutation_shard.sh` есть в обоих манифестах, а тело старого payload'а — нет
  (`KeyError: маркер не найден: '### `scripts/lint/mutation_shard.sh`'`). Разность манифестов пуста, файл уходит в
  `absent` → «не развёрнуто»;
- **«нужен приезжающим» не видит shell:** `needed_by_arrivals` обходит только импорты python (`ast`); у `.sh` их нет, и
  `source` соседней части не читается. Тот же класс, что F21 этажом выше: «не развёрнуто» отвечает про прошлое.

## Воспроизведение хозяина (временный клон Ally после наката, без объявлений)

- Мутационный гейт объявлен n/a (как у Ally) — вход выходит на объявлении раньше, чем подключает части: вреда нет.
- Гейт живой, TS-половина, Stryker-заглушка и пустой `stryker.config.json` (чтобы дойти до долей):
  - часть **отсутствует** (как оставляет накат): `line 97: …/mutation_shard.sh: No such file or directory`,
    `mutation_ts.sh: line 225: ts_shard: command not found`, `ts_counts: command not found` — **exit 0**: строка
    `ts_shard || { ts_counts 0 0; return 0; }` выходит нулём, ничего не просудив;
  - часть **на месте:** «Stryker отработал, но отчёт не найден — гейт НЕ судит» → `not_judged`, **exit 1**.

То есть на проекте с живой TS-половиной (по замеру флота 18.10 — G connect) накат 2.64+ этим инструментом возвращает
ровно то, что `cqg@2.64` закрыла: «не просудил» выходит зелёным.

## Что сделано в Ally (канон не правился)

`mutation_shard.sh` объявлен в `scripts/lint/not-applicable.json`: мутационный гейт у Ally n/a целиком (ключ
`check_mutation_gate.sh`), вход выходит на объявлении до подключения частей. Доктор — `AUTO` «развёрнуто 53 из 54,
1 объявлены неприменимыми», `DEAD 0`. Запись `kind: upstream-candidate` у `scripts/lint/mutation_shard.sh` в
`scripts/lint/adapted.json`.

## Предложение (решает судья)

- План: новая часть комплекта — та, чьего тела нет в старом payload'е (а не та, которой нет в манифесте), и она
  «новый файл» либо «нужен приезжающим», если её подключает приезжающий; для shell — разбор `source`/`.` с
  `$SCRIPT_DIR/…` (форма у частей канона одна).
- `apply_update`: копировать части комплекта вместе с входом (§5.0: «копировать надо все»).
- Тест канона: накат `2.63 → 2.64+` на раскладке с развёрнутым мутационным комплектом даёт доктору `DEAD 0`, а
  гейту с живой TS-половиной — не `exit 0` без вердикта.

## Куда уехало

- сообщение судье (сессия Prepare) после мержа поставки.
