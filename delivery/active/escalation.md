# Escalation — V3c `accent-onnx`: Z18 «до 1e-4 с onnxruntime 1.31» недостижим на ORT 1.28.0

## Что пробовал

Модели RUAccent через `AllyOnnx` (ORT 1.28.0, C API, `ORT_ENABLE_ALL`) на id всех 804 вызовов моделей, записанных в
конвейере Python на 163 позициях (`~/models/tts/ruaccent-parity/pipeline.jsonl`, onnxruntime 1.31):

| Сравнение | «ё» | омографы (turbo3.1 int8) | модель слов |
|---|---|---|---|
| Swift ORT 1.28.0 против Python onnxruntime 1.28.0 | 0,0 | 0,0 | 0,0 |
| Python 1.28.0 против Python 1.31 (= Swift против 1.31) | 0,0 | 0,038 (123 из 228 > 1e-4) | 0,171 (26 из 419) |
| Python 1.31 сам с собой: `ENABLE_ALL` против `ENABLE_BASIC` (модель слов) | — | — | 0,142 |

Перевёрнутых решений против 1.31 — 0 из 804 (омографы и «ё» — argmax, модель слов — метка ударения с порогом 0,55).
Слой Swift повторяет Python той же версии бит в бит; разница — ядра ORT между 1.28 и 1.31 в квантованных и слитых
операциях, а не код. ORT 1.28.0 выбран в V1 ради пары с sherpa-onnx (API 28).

## Какое решение нужно

Z18 подписан с порогом 1e-4 против onnxruntime 1.31 — на ORT приложения он не выполним; менять подписанное — родителю.

## Вариант A — переподписать Z18 (рекомендую)

- «Логиты моделей RUAccent на ORT 1.28.0 равны onnxruntime 1.28.0 на Python бит в бит; против 1.31 — те же решения на
  всех 804 вызовах, разница логитов ≤ 0,2». Эталон 1.28 записывается тем же скриптом стенда.
- **Цена:** подпись родителя; эталон второй версии ORT в `~/models`.

## Вариант B — поднять ORT приложения до 1.31

- **Цена:** ломается выбор V1 (API 28 — пара с sherpa-onnx 1.13.8), новая проверка слуха; V1 и поставка слуха
  переделываются. Не рекомендую.
